# 四阶段合同与交接协议

## 设计边界

总控 Skill 不规定某个 TTS、数字人模型、剪辑引擎、人物模板或文件路径。它只规定四个阶段怎样进入、怎样证明完成、怎样交接，以及上游内容版本变化时哪些下游结果需要更新。

每次执行都保留两类制品：

- **阶段原生制品**：由被绑定 Skill 按自己的合同生成，例如来源报告、WAV、批准单、数字人 MP4、封面和 QA 报告。
- **通用交接物**：由总控写入 `handoffs/`，只记录阶段 Skill、状态、审批、原生制品路径与 SHA-256，不复制或修改原生制品。

通用交接 JSON 至少包含：

```json
{
  "schema_version": 1,
  "run_id": "YYYYMMDD-project-slug",
  "stage": "script|audio|avatar",
  "status": "approved|qa_passed",
  "stage_skill": {"name": "skill-name", "version": "known-or-unknown"},
  "created_at": "ISO-8601",
  "inputs": [{"role": "source", "path": "...", "sha256": "..."}],
  "outputs": [{"role": "primary", "path": "...", "sha256": "..."}],
  "approval": {"required": true, "approved_by": "...", "approval_text": "..."},
  "native_manifest": {"path": "...", "sha256": "..."},
  "limitations": []
}
```

`approval` 只记录真实发生的用户确认。内部 QA 阶段应设置 `required: false`，不得伪造用户批准文字。未知版本如实写 `unknown`。

## 0. Preflight

进入条件：

- `workflow-profile.json` 通过结构校验。
- 已按入口一次性展示完整资料清单，用户知道后续是否需要声音参考、人物样片、品牌素材及三次确认；敏感文件仍按阶段最小化提交。
- 已读取 `profiles/onboarding-status.json` 和 `profiles/asset-center.json`；缺失时完成首次启用，存在时只补当前入口需要且为 `pending / needs_recalibration / needs_review` 的模块。`not_selected` 的无关模块不阻塞。
- 用户已明确说明用途、人物关系和最终发布者，并完成合法使用声明。
- 人物为第三方时，声音和肖像授权证据已经核验；出现公众人物、未成年人、政府/司法/金融/媒体/客服冒充、索财、删除标识或其他高风险迹象时已停止并记录。
- 四个阶段 Skill 可发现，或用户明确允许本轮只运行到某一阶段。
- `project-brief.md` 已写入人物身份、授权范围、输入真源、发布渠道、隐私边界和交付要求；需要二创或风格适配时 `creator-profile.md` 已达到最低资料标准。
- 涉及克隆声或嘴部驱动时，声音与肖像的 `consent-record.json` 或等效证据有效。
- 项目输出目录与交付目录可写，且不落在开源 Skill 目录内。

产物：`skill-contract.md`、`project-brief.md`、`task-order.json`、本地私有合法使用声明及授权证据哈希。

## 1. Rewrite

输入：一条或多条来源链接、本地视频/音频、逐字稿或用户原始材料。

阶段原生产物至少要证明：

- 来源与转写或用户输入的对应关系。
- 原内容理解与重构决策。
- 创作者资料、职业边界与本领域权威来源已经实际用于筛选案例、事实和表达。
- 原视频选题卡、1–3 条同款高表现候选与来源贡献表。
- 干净的最终口播稿。
- 原创性、事实、录制可行性或被绑定 Skill 规定的同等级 QA。

进入下一阶段前：用户明确确认最终显示稿，或明确声明用户提供的原稿无需改写。把显示稿、来源报告和 QA 哈希写入 `handoffs/script-handoff.json`。

## 2. Voice

输入：已批准的显示稿、脚本交接物、声音授权证据、被绑定声音 Skill 要求的参考材料。

阶段原生产物至少要证明：

- 显示稿与实际发音稿的关系。
- 完整音频文件、转写和音频 QA。
- 模型/参数/参考声的可追溯记录；敏感资产只记录本地引用，不进入开源包。
- 首次建档时当前人物、模型、参考声和语言组合完成参考声体检、同文案三风格盲听、独立验证，并在 `voice-profile.json` 冻结用户选择；已有有效 Profile 时不得每条重复建档，也不得借用其他人的速度倍数。
- 当前项目先生成并确认开头、最长句、英文/数字风险句，再完成全音频 ASR、响度、静音、重复、吞字、爆音与连续试听 QA。
- 英文、品牌、缩写和易错专业词已有可听中文语境在线来源、上下文试听与用户确认记录。
- 用户对最终完整音频的明确试听确认。

进入下一阶段前：批准单必须绑定最终音频内容哈希。把最终 WAV、转写、QA 和阶段原生批准单哈希写入 `handoffs/audio-handoff.json`。

## 3. Avatar

输入：已批准音频及交接物、声音/肖像授权证据、通过素材体检的真人模板，以及阶段 Skill 要求的画面参数。

阶段原生产物至少要证明：

- 输入音频哈希与音频交接完全一致。
- 画面来源和授权范围。
- 用户录制前已收到录制检查清单并确认知悉；参考视频满足时长、固定机位、单人、脸部清晰、无遮挡、无硬切和静态背景要求，并生成 `avatar-source-qa.json`。已有素材无需补造知悉记录，但必须执行同一体检。
- 内部代表性样片已覆盖主要风险点。
- 口型、动作、接缝、冻结、封装和最终音轨已按阶段 Skill 检查。

进入下一阶段前：最终数字人 MP4 的音轨仍与获批音频一致，或阶段 Skill 给出可验证的允许封装关系；用户已经观看完整画面并明确确认可以包装。把 MP4、运动 QA、音轨复核、确认原话和限制写入 `handoffs/avatar-handoff.json`。

## 4. Packaging

输入：已验证数字人/单人口播 MP4、脚本、字幕/转写、固定剪辑包装规范、素材真源表和交付规格。

阶段原生产物由所绑定包装 Skill 决定。至少包含：

- `content-hierarchy.md` 或同等级文案语义表。
- 口播触发点时间线。
- 素材真源与授权表。
- 代表性内部样片及其检查证据。
- 最终视频、要求的封面/母版/发布版、工程和 QA 报告。
- 包装固定使用 1080×1920、人物右下、黑色背景、青蓝强调，并交付无封面版、带封面版与 9:16/3:4/1:1 三张封面；不询问或暴露历史版本编号和内部母版名。

最终生成 `delivery-manifest.json`，列出每个必交文件的路径、SHA-256、字节数、媒体参数、QA 状态和已知限制。

## 版本一致性矩阵

文件是否能播放，与它是否匹配当前任务版本是两件事。只有直接输入内容哈希变化，才把相关下游阶段标记为 `needs_update`；旧制品始终保留为 `historical`。

| 发生变化 | 当前任务需要更新 | 不需要更新的情况 |
|---|---|---|
| 来源或研究材料 | 先复核二创证据；只有最终批准口播稿哈希变化时，数字人音频、画面和包装才需更新 | 来源补充但最终批准口播稿哈希不变 |
| 最终批准口播稿 | 数字人音频、数字人画面、剪辑包装 | 只改文件名、注释或不进入口播的说明 |
| TTS稿、模型、参数或参考声 | 重新检查/生成数字人音频；只有最终获批音频哈希变化时，画面和包装才需更新 | 参数调整后最终获批音频哈希仍相同 |
| 最终获批音频 | 数字人画面、剪辑包装 | 只移动文件且内容哈希不变 |
| 人物模板、裁切或口型生成参数 | 重新检查/生成数字人画面；只有最终人物 MP4 内容变化时，包装才需更新 | 模板元数据变化但最终人物 MP4 与音轨哈希均不变 |
| 最终人物 MP4 | 剪辑包装 | 只改文件名且内容哈希不变 |
| 包装字幕、素材、触发时间或导出参数 | 剪辑包装及最终 QA | 与发布文件无关的工程注释 |

需要更新时保留历史文件和原批准记录，给旧交接物标记 `historical: true`；不得删除证据，也不得让绑定旧哈希的批准自动批准新版本。

## 兼容现有 Skill

现有专用 Skill 无需改动。只要 Profile 把四个阶段分别绑定到它们，总控在每个阶段读取并完整执行原 Skill，再用通用交接物引用其原生输出即可。若原 Skill 的要求比本合同严格，以更严格者为准。
